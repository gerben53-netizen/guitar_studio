# NoteEvent and positional adapters

The authoritative multi-track event remains the existing NoteEvent: id, note/rest, exact start/duration and tones, with optional descriptive technique metadata. TrackEvent adds only measureId and requires reduced whole-note fractions. Chords remain one event with simultaneous tones; another independent event can start at the same instant on another string with a different duration. Nothing turns horizontal source columns into timing.

Existing `validateMeasure` performs exact BigInt boundary/overlap comparisons and physical pitch/profile validation. The adapter removes only measureId before invoking that existing strict validator. No duplicate theory/overlap implementation was introduced. A same-string overlap is rejected; simultaneous different strings are valid. Rests retain empty tones; links cannot point to rests. Technique labels (normal, hammer-on, pull-off, slide, bend, vibrato, mute) are metadata, not a claim of physical articulation simulation; previous documents had no technique field, so the optional shared field preserves compatibility.

`positionalEvents` projects an event to one entry per tone (or one rest), with original group ID, tone index/count, unchanged timing and metadata. `groupedEvents` reconstructs groups only when timing/kind/technique/count agree and every tone index is present once. Missing or inconsistent groups fail explicitly. Independent groups sharing a start stay independent. Tests compare complete original events in both directions, including chord tones, differing polyphonic durations, rests, physical positions, pitch and technique. The representation is a transient adapter, not a second persisted event source.

Legacy v1 conversion keeps all event/measure/section IDs. Fractions are reduced explicitly; their rational values do not change. Normalized fixtures round-trip byte-semantically as JSON; unreduced source fractions retain their exact original form in backups/history while canonical storage uses equivalent reduced values. v1 permits profile ranges above fret 24 and custom token shapes; unsupported actual high-fret content or embedded-newline tokens fails conversion for review and leaves original storage intact. It is never truncated or guessed. No automatic blanket migration claims are made for arbitrary unknown production documents.
