# Lyrics Alignment Mode (#76)

Alignment is a contextual mode of `WorkspaceV3`, rendered above the existing `ScoreSystem`. It reuses the score, saved lyric lanes, track controls and Design System v2. Three entries capture the current arrangement, track, lyrics section/line and selection. Selected NoteEvent IDs take precedence over explicitly selected measures; otherwise the active track supplies its notes across the arrangement. Chord tones are deduplicated by event ID. Independent simultaneous events remain separate, ordered by exact rational cross-products and then ID. Rests are excluded. Pitch-only notes have a selectable MIDI label without an invented fingering.

`lyrics-alignment.ts` owns a typed, pure `AlignmentSession`: source fingerprint/revision, immutable source notes/syllables/links, current cursors, candidate links, skipped syllables, explicit conflict decisions, and separate past/future stacks. The production vocabulary is schema-v2 `lyricsLinks` and `sustain`, rather than the prototype's `links`/`hold`. No alternate document schema, localStorage draft, migration, playback timing or editor render loop was introduced.

The toolbar supports sequential binding, melisma across measures, skip, correction, sustain, explicit previews and keyboard routing. A new sequential candidate starts empty. Melisma appends to the current candidate; when editing an existing link it preserves its other source notes. A candidate's already assigned note moves between concept syllables; persisted links always require a conflict decision. Unchanged links retain identity and timestamps. Replacing an overlapping note trims only that note from another melisma. A keep decision protects the original complete link against competing replacements. Contradictory candidate assignments block confirmation.

A proposal maps only the first `min(notes, syllables)` pairs and reports unequal counts. Its checkpoint includes the complete previous draft and both undo stacks; cancelling restores all three exactly. Editing and ordinary concept Undo/Redo remain separate from the document's undo history. Selecting a different line is allowed before drafting; afterwards the user must finish or discard the current work first.

Opening the mode locks document mutations and flushes any earlier ordinary edits before capturing the source revision. Candidates never enter `useSong.document` or ordinary autosave. Root navigation, import/create, arrangement changes, ordinary fret editing, Practice and document Undo/Redo are guarded. Track switching offers continue, review, or explicitly discard and switch. Cancellation restores the prior selection/cursors and entry focus without writing alignment changes. A deliberate track switch can subsequently save the ordinary active-track preference. Browser unload warns while a session is active.

Confirmation revalidates the normalized source fingerprint, all references and conflicts, replaces only the target arrangement's intended links and validates the complete resulting schema-v2 document. `useSong.commitDocument` serializes with any pending request and uses the existing revision-aware canonical PUT endpoint. The existing PostgreSQL transaction locks the row, checks owner/revision, validates the document, updates current and inserts history atomically. Only a successful response installs the canonical document and adds one ordinary undo snapshot. A failed request, rollback or 409 leaves the editor document/history and the in-memory candidate intact. Retry is safe after a definite failed response. If the server source changed, explicitly discard and reload before starting a fresh session; the UI does not automatically overwrite the winner. Existing schema-1 backup/upgrade confirmation is incorporated into explicit preview confirmation.

The source fingerprint normalizes schema field order before comparing, so PostgreSQL JSONB key ordering does not produce a false source change. Neither a full-document PUT nor optimistic concurrency can make an ambiguous network response exactly-once: if a response is lost after a server commit, retry receives 409 and preserves the draft; reload the canonical version before further edits. This uses the existing API contract without introducing a second persistence mechanism.

Semantic scoped CSS in the existing screens layer supplies sticky context, text/icon statuses, draft lanes separate from saved lanes, horizontal internal strips and responsive wrapping. Native fields/contenteditable and open dialogs retain native keyboard behavior. The current syllable and current event receive independent visible indicators; automatic scrolling targets the internal score and strip. The shared native dialog supplies focus trapping/restoration, busy confirmation prevents repeated submissions, and reduced motion is respected.

Validation is local against the React app, installed Windows Chrome and a separate PostgreSQL test database. The accepted prototype is a behavior reference, not production test evidence. See the 38-scenario matrix and machine-readable artifacts in `docs/qa/issue-76-acceptance.md`. Bass/instrument expansion (#75), other browsers, physical touch and screen-reader certification remain outside this change.
